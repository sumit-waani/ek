# Audit fixes: regex arg order, datetime tokens, CSRF idempotency, math int-return, request.form

Five divergences between the Eka builtin documentation and the C implementation are corrected in a single pass across `builtins.c`: regex.replace had its subject/replacement args swapped, datetime.parse passed raw Eka format tokens to strptime without conversion, session.csrf() regenerated tokens on every call, math functions always returned doubles even for whole numbers, and request.form() was a stub. Each fix is accompanied by a new test, and three pre-existing test assertions are updated to match the corrected behavior.

Watch for: request.form() does not validate `%`-encoded sequences and will silently produce NUL bytes on malformed input like `%ZZ` (confirmed). The math int-conversion guard `r == floor(r)` is tautologically true inside `math_floor`, `math_ceil`, and `math_round` — harmless but worth noting for readability (confirmed).

**Verdict**: APPROVED

## High-level view

The regex.replace fix swaps args[1] and args[2] and updates the fallback-on-error return from `args[2]` to `args[1]` (the subject), matching the documented signature `regex.replace(pattern, subject, replacement)`.

The datetime.parse token conversion replicates the same branching structure already present in `datetime_format`, translating Eka tokens (YYYY, MM, DD, HH, mm, ss) to C strptime specifiers before parsing. The two APIs are now symmetric.

The session.csrf() idempotency fix checks for an existing `_csrf` key in the session map before generating a fresh token. Note: the pre-existing mismatch between the key used here (`_csrf`) and the one server.c's CSRF verifier looks up (`_csrf_token`) is out of scope for this diff but means CSRF verification is broken on main regardless of this fix.

The math int-return change applies the same guard pattern (`fits in 46-bit signed range`) already used by `number.parse` to all five math functions (floor, ceil, round, min, max).

The request.form() implementation is a URL-decode loop mirroring request_query: `+`-as-space, `%XX` hex pairs, per-pair malloc. The gap is malformed percent-encoding — `strtol` on invalid hex digits silently returns 0, embedding NUL bytes in decoded strings.

<summary>Issues (2)</summary>

1. **Invalid hex in percent-encoding silently produces NUL** — In request_form's URL-decode loop, `strtol("ZZ", NULL, 16)` returns 0, so `%ZZ` becomes a NUL byte embedded in the decoded string. Eka's length-aware strings won't truncate, but any downstream C code calling `strlen()` on the raw `data` pointer will see a truncated string. Consider validating hex digits before decoding.
2. **Redundant wholeness check in floor/ceil/round** — `r == floor(r)` is always true when `r` is already the result of `floor()`, `ceil()`, or `round()`. The check is harmless but makes the code look like there's a condition that could be false. A comment or removing the tautology would clarify intent.

## request.form URL-decode and NUL injection

The decode loop:

```c
if (c == '%' && si + 2 < val_raw_len) {
    char hex[3] = {val_start[si + 1], val_start[si + 2], '\0'};
    val_dec[vi++] = (char)strtol(hex, NULL, 16);
    si += 2;
}
```

The bounds guard (`si + 2 < val_raw_len`) is correct — a `%` at position `len - 2` fails the guard and is emitted as a literal. The risk is `strtol` interpretation: a body containing `%ZZ` produces `(char)0`. The `vi`/`ki` length counters track the true decoded length, so Eka's length-aware strings handle embedded NULs. But C code that calls `strlen()` on `eka_string->data` — which appears in template rendering, logging, and SQL parameter binding — would see truncation at the injected NUL. This is the same behavior as the existing `request_query` path, but since request_form handles untrusted POST bodies at higher volume, it's the more exposed surface.

## datetime.parse token ambiguity

The token set uses case to distinguish month (`MM`) from minute (`mm`). A format string like `"YYYY-MM-DD HH:MM:ss"` (uppercase MM for both month and minute) would silently produce month in both positions. This matches `datetime.format`'s behavior and the documented token list, so it's consistent — but the risk of user confusion is real and undocumented.

## Test coverage gaps

Not tested: request.form with percent-encoded keys/values, request.form with missing `=` (key-only parameter), request.form with empty body vs null body, math functions with values near the 46-bit boundary, datetime.parse with partial token matches (e.g., a single `M` in the format string).
